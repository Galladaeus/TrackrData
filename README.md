# TrackrData

TrackrData is an Android class project for recording location samples, detecting visits to saved places, and exploring visit patterns on an interactive map.

The app combines manual visit logging with automatic arrival/departure detection. It also highlights frequently visited places and nearby pairs of places that might be convenient to visit together.

## Features

- **Map:** ArcGIS basemap with saved-place markers sized by recorded visit count.
- **Heatmap:** Switch between markers and a visit-weighted heatmap showing recorded visit concentration.
- **Location tracking:** Record GPS samples during an active tracking session and display them as blue map points.
- **Saved locations:** Capture the current position as a saved place and view visit counts and latest-visit dates.
- **Visits:** Start and end visits manually, or record them automatically while tracking.
- **Insights:** View total recorded visits, visited-place counts, frequently visited places, and nearby-place suggestions.
- **Local persistence:** Store saved places, visits, and location samples in a Room database.

## Setup

### Requirements

- An Android Studio version compatible with the project's Android Gradle Plugin.
- Android SDK platform **37** (the current compile and target SDK).
- An emulator or device running **Android 9 / API 28 or newer**, with Google Play services for location functionality.
- Internet access for dependency downloads and the online ArcGIS basemap.
- An ArcGIS API key with access to the required basemap services and a suitable ArcGIS Maps SDK license key.

Use a Gradle JDK compatible with the Android Gradle Plugin; the Java source/target compatibility setting in this project is 17.

### Configure credentials

1. Clone the repository and open its root folder in Android Studio.
2. Create or update `local.properties` in the project root. Keep the `sdk.dir` entry generated by Android Studio and add:

   ```properties
   ARCGIS_API_KEY=your_arcgis_api_key
   ARCGIS_LICENSE_KEY=your_arcgis_license_key
   ```

   Enter the values without surrounding quotes. Both properties are required by the build.

3. Sync the project with Gradle.
4. Select the `app` run configuration and an emulator or connected device.
5. Run the app and grant location permission when prompted. Precise location is recommended for visit detection.

`local.properties` is ignored by Git. Do not commit credentials or share database exports containing personal location history. The build embeds the configured values in the app, so use appropriate API-key restrictions rather than treating an APK as secret storage.

### Command-line build

From the repository root in Windows PowerShell:

```powershell
.\gradlew.bat :app:assembleDebug
```

Run local unit tests with:

```powershell
.\gradlew.bat :app:testDebugUnitTest
```

On macOS/Linux, use `./gradlew` instead of `.\gradlew.bat`. These commands also require the SDK, compatible JDK, and credential configuration above.

## Using the app

1. Open **Locations** and use the location capture action to save a place at your current position.
2. Open **Map** and select **Start Tracking** to begin recording location samples.
3. Stay near a saved place long enough for automatic visit confirmation, then move away to trigger departure detection.
4. Use **Visits** to review records or manually start and end a visit.
5. Switch between **Markers** and **Heatmap** on the map.
6. Open **Insights** to compare visit frequency and review nearby-place suggestions.

For emulator testing, supply a simulated location using the emulator's location controls. Automatic detection requires multiple readings over time, not just a single coordinate change.

### Automatic visit detection

The current default thresholds in [`VisitDetector.kt`](app/src/main/java/com/example/trackrdata/utils/VisitDetector.kt) are:

| Setting | Default |
| --- | --- |
| Arrival radius | 100 meters |
| Arrival dwell time | 2 minutes |
| Required arrival samples | 3 |
| Exit radius | 150 meters |
| Departure dwell time | 1 minute |
| Maximum accepted accuracy radius | 50 meters |
| Maximum gap between readings | 30 seconds |

Missing or inaccurate readings reset pending detection evidence. Tracking-session cleanup attempts to close any automatic visit being recorded, with notes explaining interrupted observations.

## Interpreting the data

- A **location** is a saved place.
- A **location sample** is an individual GPS measurement.
- A **visit** is a recorded stay associated with a saved place. Sample count is not visit count.
- Visit counts include ongoing visits and use all recorded history.
- The heatmap uses one point per saved place, weighted by its visit count. Places with zero visits do not contribute heat. It does not require GPS samples to show existing visits.
- Heatmap colors show relative visual concentration; nearby points can blend together, and the appearance depends on zoom and renderer settings. They do not represent traffic, routes, distance traveled, or a calibrated geographic density measurement.
- Nearby suggestions currently consider places with at least two visits each, separated by approximately 50–1,000 meters, and show up to three pairs ordered by distance. Distances are straight-line geographic distances, not road or walking routes.

## Database and demo data

The local database is named `app_database`, currently at **schema version 4**. Room schema exports are stored in `app/schemas/`.

The current database builder does not bundle a demo database or provide an in-app import/restore action. A fresh installation without an Android-restored backup starts with no saved records. Existing records can be inspected or exported through Android Studio's **App Inspection → Database Inspector**.

Database backups must match the expected Room schema or have a supported migration path. Back up existing data before replacing a database, and never replace its files while the app is running. Clearing app storage removes its local records.

If synthetic visits are used for a presentation, identify them as demo data rather than real recorded travel.

## Limitations

- **Tracking is foreground-only:** collection stops when the activity receives `ON_STOP`, such as when the app is hidden. There is no background tracking service.
- Automatic visits depend on GPS accuracy, sampling continuity, and proximity to previously saved places.
- Interrupted tracking can split one physical stay into multiple recorded visits.
- Map sample visualization is scoped to the selected tracking session; it is not a complete historical route view.
- Suggestions are simple frequency-and-distance rules, not AI recommendations, route optimization, or guaranteed trip savings.
- The online basemap requires network access and valid ArcGIS configuration.
- This is a class project, not a safety-critical or production-grade location monitoring system.
